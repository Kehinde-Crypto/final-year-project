# Supply Chain Smart Contracts

This directory contains the smart contract layer of the project. It is built with Hardhat and is responsible for defining the on-chain supply chain rules, validating who can do what, recording product movement, and emitting the blockchain events that the rest of the project depends on.

The main contract in this folder is `contracts/SupplyChain.sol`.

## What this folder is responsible for

The smart contract layer is the source of truth for supply chain activity. It defines:

- who can register as an actor
- which role an actor has in the supply chain
- who is allowed to create a product
- how a product is transferred between actors
- which transfers are valid and which ones must be rejected
- how product history is stored and queried
- which events are emitted for off-chain services to consume

In this project, the contract is not just a storage layer. It also enforces the business rules of the supply chain.

## Main contract

`contracts/SupplyChain.sol` contains the business logic for:

- actor registration
- actor deactivation
- product creation
- product transfer
- product status updates
- product recalls
- view functions for reading actors, products, counts, and transfer history

### Important rules enforced by the contract

The contract currently enforces these key rules:

- only registered and active actors can participate
- only active manufacturers can create products
- a product must exist before it can be transferred
- only the current owner can transfer a product
- recalled or sold products cannot be transferred
- transfers must follow the allowed path:

```text
Manufacturer -> Supplier -> Distributor -> Retailer -> Consumer
```

That means the contract itself protects the supply chain flow. If someone tries to skip a role, the transaction reverts and no state change is written to the blockchain.

## What each directory does

### `contracts/`

This contains the Solidity source files.

- `SupplyChain.sol` is the contract that gets compiled into EVM bytecode
- this is the file you edit when changing on-chain logic
- any change here usually requires recompiling and retesting

### `scripts/`

This contains TypeScript scripts that run against the contract.

- `deploy.ts` deploys the contract to a blockchain network
- `seed.ts` fills the deployed contract with example data

These are not tests and they are not part of the contract itself. They are off-chain automation scripts.

### `test/`

This contains automated test files.

- `SupplyChain.test.ts` checks whether the contract behaves correctly
- tests deploy fresh contract instances and simulate real transactions
- this helps catch mistakes before deployment

### `artifacts/`

This is generated by Hardhat after compilation.

It contains the compiled outputs of the contract, especially:

- the ABI
- the bytecode
- build metadata

This folder is extremely important because deployment tools, tests, frontends, and event-processing services all rely on these generated files.

### `cache/`

This is also generated by Hardhat.

It stores compilation cache data so that future builds are faster. Hardhat uses it to avoid recompiling unchanged files.

This folder is not the contract itself and is safe to regenerate.

### `deployments/`

This stores deployment results produced by your custom deployment script.

In this project, `deployments/localhost.json` records:

- contract name
- deployed address
- chain id
- deployer address
- block number
- deployed timestamp
- ABI

That file is useful because the frontend or transformer can read it to know where the contract lives.

### `ignition/`

This is for Hardhat Ignition, which is a deployment system for managing deployment modules.

In your current setup, the project is using `scripts/deploy.ts` rather than an Ignition deployment flow, so this folder is present for Hardhat structure and future expansion, but it is not the main deployment mechanism right now.

### `hardhat.config.ts`

This is the central Hardhat configuration file.

In your project it defines:

- Solidity version: `0.8.20`
- optimizer settings
- `viaIR: true`
- EVM version: `paris`
- configured networks

This file affects how the contract is compiled and which networks Hardhat can connect to.

## Command walkthrough

Below is the recommended command flow and what each command actually does.

## 1. Install dependencies

```bash
npm install
```

### What it does

This reads `package.json` and installs the development dependencies for the smart contract environment.

That includes packages such as:

- Hardhat
- TypeScript
- viem
- Hardhat plugins
- dotenv

### What it affects

It creates or updates:

- `node_modules/`
- `package-lock.json`

### Why it matters

Without this step, Hardhat commands such as compile, test, and deploy will not work because the required tooling is not available locally.

### Effect on the smart contract

It does not change the contract itself. It only prepares the development environment.

## 2. Compile the contract

```bash
npx hardhat compile
```

If you want to ignore old cached results and force a fresh compilation:

```bash
npx hardhat compile --force
```

### What it does

This command:

1. reads the Solidity source from `contracts/SupplyChain.sol`
2. uses the compiler settings from `hardhat.config.ts`
3. compiles the contract into EVM-compatible output
4. writes the outputs into `artifacts/`
5. stores compiler cache information in `cache/`

### What gets generated

The most important generated file is typically:

`artifacts/contracts/SupplyChain.sol/SupplyChain.json`

That file contains:

- ABI
- bytecode
- deployed bytecode
- metadata

### Why the ABI matters

The ABI tells external tools how to interact with the contract.

For example, it describes functions like:

- `registerActor`
- `createProduct`
- `transferProduct`
- `recallProduct`
- `getProduct`
- `getCounts`

Without the ABI, your frontend, tests, and scripts would not know how to call the contract.

### Why the bytecode matters

The bytecode is the actual low-level code that gets deployed to the EVM. When you deploy the contract, it is the bytecode that is sent to the EVM.

### Effect on the smart contract

Compilation does not deploy anything and does not change blockchain state. It transforms your source code into deployable output.

### Effect on related folders

- `artifacts/` is created or updated
- `cache/` is created or updated

## 3. Run the tests

```bash
npx hardhat test
```

### What it does

This command runs the automated tests in `test/SupplyChain.test.ts`.

Hardhat creates a temporary in-memory blockchain environment for the tests. The tests then deploy fresh contract instances and simulate transactions against them.

### What your test file is checking

Your tests currently cover:

#### Actor Management

- registering actors
- registering all supply chain roles
- preventing duplicate registration
- deactivating an actor

#### Product Management

- creating a product
- blocking non-manufacturers from creating products
- retrieving product details
- recalling a product

#### Product Transfer

- transferring from manufacturer to supplier
- enforcing the correct chain flow
- completing the full product journey
- recording transfer history

#### View Functions

- total counts
- products by owner

#### Edge Cases

- non-existent product transfers
- recalled product transfers
- non-owner transfers

### Why this matters

Smart contracts are difficult to fix after deployment. Testing reduces the risk of deploying invalid business logic.

In your project, the tests prove that:

- permissions are enforced correctly
- transfer order is enforced correctly
- product ownership changes correctly
- status transitions behave as expected
- invalid actions revert safely

### Effect on the smart contract

The tests do not affect your persistent local deployment. They run in a temporary environment and disappear after the command ends.

### Result from the rerun

I reran this command and all 17 tests passed.

## 4. Start the local Hardhat blockchain

```bash
npx hardhat node
```

### What it does

This starts a local Ethereum-compatible blockchain node for development.

It provides:

- a local JSON-RPC endpoint
- pre-funded test accounts
- a persistent dev chain while the process is running

### Why it matters

Unlike `npx hardhat test`, this node stays running so that other scripts can connect to it.

That means:

- `deploy.ts` can deploy to it
- `seed.ts` can send transactions to it
- MetaMask can connect to it
- the frontend can read from it
- the transformer can listen for events from it

### Effect on the smart contract

This command does not deploy the contract by itself. It only starts the blockchain environment where deployment can happen.

### Important note

You normally keep this command running in one terminal while using a second terminal to deploy and seed.

## 5. Deploy the contract

```bash
npx hardhat run scripts/deploy.ts --network localhost
```

### What it does

This executes `scripts/deploy.ts` against the running local network.

The script:

1. connects to the local blockchain
2. deploys the `SupplyChain` contract
3. reads the compiled ABI from `artifacts/`
4. creates the `deployments/` folder if needed
5. writes deployment metadata into `deployments/localhost.json`

### What this means for the contract

This is the moment the contract actually becomes live on-chain.

Before deployment:

- you only have source code and compiled output
- there is no contract instance on the blockchain

After deployment:

- a real contract instance exists on the local chain
- it has an address
- it has state variables initialized by the constructor
- other services can now call it

### Constructor effect

When deployed, the constructor in `SupplyChain.sol` runs once. It sets:

- `owner = msg.sender`
- `productCount = 0`
- `transferCount = 0`

So deployment creates the initial clean state of the contract.

### Why `deployments/localhost.json` matters

This file connects the smart contract layer to the rest of your project.

It is useful because it stores:

- the address where the contract was deployed
- the ABI required to call it
- chain metadata

Without this file, off-chain code would need to manually know the contract address.

### Effect on related folders

- `deployments/` is created or updated
- `deployments/localhost.json` is written

## 6. Seed the contract with test data

```bash
npx hardhat run scripts/seed.ts --network localhost
```

### What it does

This script connects to the already deployed contract and populates it with sample data.

It reads `deployments/localhost.json` first, so it knows which contract address to use.

### What the seed script does in this project

It performs three major tasks:

#### A. Register actors

The script registers sample participants such as:

- manufacturer
- supplier
- distributor
- retailer
- consumer

This directly affects the `actors` mapping and `actorList` array in the contract.

It also emits `ActorRegistered` events.

#### B. Create products

The script creates several sample products.

This directly affects:

- `productCount`
- `products`
- `productIds`
- `actorProducts`

It also emits `ProductCreated` events.

#### C. Transfer products

The script transfers products between participants.

This directly affects:

- `transferCount`
- `transfers`
- `productTransferHistory`
- `currentOwner`
- `updatedAt`
- `status`

It also emits `ProductTransferred` events.

### Why seeding matters

Deployment gives you an empty contract instance. Seeding gives that instance useful data.

Without seeding:

- the contract exists, but has no actors
- no products exist
- no transfer history exists
- the transformer has little or nothing meaningful to consume
- the frontend has no real demo data to display

### Important observation about your current seed script

Your seed script currently includes this transfer:

```ts
{ productId: 3n, from: manufacturer, to: distributor, location: "Direct shipment", notes: "Express delivery" }
```

But your contract only allows:

```text
Manufacturer -> Supplier
Supplier -> Distributor
Distributor -> Retailer
Retailer -> Consumer
```

So this specific seeded transfer does not match the contract rules and would revert on a fresh run against the deployed contract.

That means:

- compile works
- tests work
- deploy should work
- seed may fail unless that invalid transfer is removed or changed

## What `artifacts/` really contains

The `artifacts/` folder is generated by compilation.

You can think of it as the build output of the contract layer.

It contains the files required by tools that need to:

- deploy the contract
- call contract functions
- decode events
- inspect build metadata

For your project, the most important practical use of `artifacts/` is that `deploy.ts` reads the ABI from there before writing `deployments/localhost.json`.

## What `cache/` really contains

The `cache/` folder contains temporary compiler-related information used by Hardhat to make repeated builds faster.

### Why it exists

If Hardhat had to fully recompile every file every time, development would be slower. The cache helps Hardhat remember previous build information.

### Does it affect blockchain state

No. It affects development speed, not on-chain data.

### Can it be deleted

Yes. Hardhat can regenerate it.

If needed, you can clean generated build output with:

```bash
npx hardhat clean
```

That removes generated compile outputs so they can be rebuilt from scratch.

## What `deployments/` really contains

This folder contains deployment records created by your own script.

For this project, `deployments/localhost.json` is especially important because it is a bridge between:

- the smart contract
- the frontend
- the transformer

It gives off-chain code a reliable place to find the local contract address and ABI.

## What `ignition/` really contains

The `ignition/` folder is for Hardhat Ignition deployment modules.

Hardhat Ignition is useful for more structured deployment workflows, especially in larger or multi-contract projects.

In your current project:

- deployment is handled by `scripts/deploy.ts`
- ignition is not the active deployment path

So this folder matters conceptually, but not operationally for your current local workflow.

### Test 4 — Seed Script Bug Found & Fixed

**First run of seed — failed with:**
```
ContractFunctionExecutionError: The contract function "transferProduct" reverted with the following reason:
Invalid transfer: must follow supply chain path (Manufacturer->Supplier->Distributor->Retailer->Consumer)

args: (3, 0x90f79bf6eb2c4f870365e785982e1f101e93b906, Direct shipment, Express delivery)
sender: 0x70997970c51812dc3a010c7d01b50e0d17dc79c8
```

**Root cause:** Line 89 of `scripts/seed.ts` tried to transfer Product 3 directly from Manufacturer to Distributor, skipping the Supplier — which the smart contract correctly rejects.

**Fix applied in `scripts/seed.ts`:**
```diff
- { productId: 3n, from: manufacturer, to: distributor, location: "Direct shipment", notes: "Express delivery" }
+ { productId: 3n, from: manufacturer, to: supplier, location: "Shenzhen Warehouse", notes: "Express shipment" },
+ { productId: 3n, from: supplier, to: distributor, location: "Singapore Port", notes: "Express delivery" },
```

**Why this bug matters:** This actually demonstrates that the smart contract is working correctly. It caught an invalid business rule violation and reverted the transaction — exactly as designed.
